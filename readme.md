# С2000-ПП (Болид) через С2000-Ethernet: библиотека, утилиты, интеграция Home Assistant

Версия 2.1.0. Протокол подробно разобран в [`agents.md`](agents.md) — там же список ловушек.

## Состав

```
/c2000pp.py                    библиотека (asyncio, только stdlib, Python ≥ 3.9) + CLI
/test_c2000pp.py               26 тестов, эмулятор конвертера внутри
/bench_c2000pp.py              замер скоростей/задержек, таймлайн взятия/снятия шлейфа
/pcap_decode.py                расшифровка tcpdump-захватов
/readme.md, /agents.md         эта документация и разбор протокола
/custom_components/bolid/      интеграция Home Assistant (внутри — копия c2000pp.py)
```

> Копия `c2000pp.py` в `custom_components/bolid/` должна быть **идентична** корневой
> (HA не умеет импортировать из-за пределов папки интеграции).

## Как это устроено

```
приборы Орион —RS-485— С2000-ПП —RS-485/Modbus— С2000-Ethernet —UDP:40002— HA / PC
```

* Конвертер рассылает **каждый ответ на все настроенные в нём IP**, на фиксированный порт 40002.
  Поэтому клиент слушает локальный порт 40002 и видит и свои ответы, и ответы на запросы других.
* Modbus на шине один: запросы **строго по очереди**. Ответ в Modbus не содержит ID запроса,
  поэтому каждый ответ проверяется (IP, заголовок, длина, CRC, адрес, функция, форма данных).
* Фоновые задачи клиента: **опрос всех зон** по расписанию (по умолчанию 10 с) — независимо от
  **слушателя**, который принимает всё, что приходит в порт, и **команд**, идущих вне очереди опроса
  (приоритет выше).

## 1. Библиотека `c2000pp.py`

### 1.1 Минимальный пример — один разовый опрос

```python
import asyncio
from c2000pp import C2000PP

async def main():
    pp = C2000PP("192.168.1.10", 40002, zones=range(1, 17))
    await pp.t.start()                 # только сокет; фоновый опрос не нужен
    try:
        print(await pp.read_device_info())      # {'type': 36, 'version': '3.01', 'mode': 'slave', ...}
        await pp.poll_all()
        for n, z in pp.zones.items():
            print(n, z.status, z.code, z.name, "ВЗЯТА" if z.armed else "снята")
    finally:
        await pp.stop()

asyncio.run(main())
```

### 1.2 Постоянный мониторинг с подписчиком

```python
import asyncio
from c2000pp import C2000PP

def on_event(name, payload):
    if name == "zones":                       # payload: set номеров изменившихся зон
        for n in sorted(payload):
            z = pp.zones[n]
            print(f"зона {n}: {z.name} [{z.status}] armed={z.armed}")
    elif name == "availability":              # True/False – есть ли связь
        print("связь:", "есть" if payload else "ПОТЕРЯНА")
    elif name == "foreign_command":           # другой клиент взял/снял зону
        print("чужая команда:", payload)      # {'zone': 2, 'code': 24}

async def main():
    global pp
    pp = C2000PP("192.168.1.10", zones=range(1, 21), poll_interval=10, stale_timeout=40)
    pp.add_listener(on_event)
    async with pp:                            # start()/stop()
        await asyncio.sleep(3600)

asyncio.run(main())
```

События подписчика: `"zones"`, `"availability"`, `"poll"` (итог цикла: `ok`, `changed`, `aborted`,
`duration`), `"foreign"` (чужой ответ на чтение), `"foreign_command"`, `"event"` (событие журнала).
Колбэки вызываются в потоке event loop, **быстро**, без блокировок.

### 1.3 Взять / снять шлейф

```python
async with C2000PP("192.168.1.10", zones=[1, 6]) as pp:
    ok = await pp.set_armed(1, True, wait=10)     # команда + ждём подтверждения до 10 с
    print("взят" if ok else "не подтвердился за 10 с", pp.zones[1].name)

    await pp.arm_zone(6)                          # без ожидания
    print(pp.zones[6].armed, pp.zones[6].pending) # True True  – ждём подтверждения (целевое)
    await asyncio.sleep(4)
    print(pp.zones[6].armed_actual, pp.zones[6].name)   # реальное состояние, напр. 'Взятие входа на охрану'

    await pp.disarm_zone(6)
    await pp.arm_section(1)                       # раздел (регистр 44096+)
```

`ZoneData.armed` — *эффективное* состояние (целевое, пока идёт подтверждение, затем реальное),
`armed_actual` — только то, что сообщил ПП. «Взята» = код 24 или 23 (задержка взятия).
Пожарный шлейф после снятия показывает **112** «Отключение ШС», а не 109 — это нормально.

Команда может упасть: `ModbusException(4)` (нет связи с прибором / управление запрещено в
конфигурации ПП), `C2000Timeout`. В обоих случаях pending снимается.

### 1.4 Реле

```python
await pp.set_relay(3, True)
print(await pp.read_relays(1, 8))        # [False, False, True, ...]
```

### 1.5 Журнал событий (разрушающее чтение! см. §3.3)

```python
pp = C2000PP("192.168.1.10", zones=range(1, 21), use_events=True, event_interval=2.0)
pp.add_listener(lambda n, p: print(p.name, p.zone, p.user, p.time) if n == "event" else None)
async with pp:
    await asyncio.sleep(600)

# или вручную, по одному событию:
ev = await pp.read_oldest_event(mark_read=True)   # None, если журнал пуст
```

### 1.6 Низкий уровень (сырые Modbus-запросы через тот же транспорт)

```python
regs = await pp.t.read_holding(40000, 8)           # состояния зон 1..8 (8 регистров)
bits = await pp.t.read_discrete(8, 4)              # режим, связь с мастером, тампер, питание
await pp.t.write_register(40000, 24)               # зона 1 ← «взять»
print(pp.t.stats, pp.t.rtt_stats())                # счётчики и задержки
```

### 1.7 Статусы зоны (`ZoneData.status`)

| status | Значение |
|---|---|
| `ok` | свежие данные |
| `pending` | ещё ни разу не получали |
| `no_data` | ПП отвечает ошибкой (зоны нет в БД / данных нет); перечитывается раз в 60 с |
| `timeout` | давно не обновлялась (`stale_timeout`) — «ошибка таймаута» |

### 1.8 Параметры `C2000PP(...)`

| Параметр | По умолч. | Описание |
|---|---|---|
| `host`, `port` | —, 40002 | конвертер |
| `slave_id` | 1 | Modbus-адрес ПП |
| `zones` | () | номера зон 1..512 |
| `poll_interval` | 10 | период опроса, с (можно 1) |
| `stale_timeout` | `max(3×poll+5, 30)` | после скольких секунд без обновления зона = `timeout`. Если ≤ периода — автоматически увеличивается с предупреждением |
| `group_size` | 8 | зон в одном запросе (1..100) |
| `use_events` | False | читать журнал ПП (разрушающе) |
| `event_interval` | 2 | период проверки журнала, с |
| `refresh_on_foreign` | True | реагировать на чужие ответы/команды |
| `pending_timeout` | 15 | сколько ждать подтверждения команды, с |
| `local_port` | = port | локальный UDP-порт (ответы идут на него) |
| `timeout`, `retries` | 1.5, 2 | ожидание ответа на один запрос / число повторов при таймауте |
| `gap` | 0.02 | пауза между запросами, с |
| `quarantine` | 0.4 | после таймаута отбрасывать запоздавшие ответы, с |

python c2000pp.py 192.168.1.10 monitor --zones 1-20 --interval 10 -v   # -v: подробный лог (битые, чужие, отброшенные кадры)

## 2. Замер скоростей: `bench_c2000pp.py`

Запускать **вне HA** на машине, чей IP прописан в конвертере, **остановив интеграцию** (иначе оба
процесса будут делить порт 40002). Утилита непрерывно слушает порт и пишет **каждую**
датаграмму (свои запросы, ответы, чужие ответы, heartbeat) в `bench_<время>.log`, итоги — в `.json`.

```bash
# безопасно (ничего не пишет в ПП): слушать, задержки, группы, стресс по паузе, события
python bench_c2000pp.py 192.168.1.10 --zones 1-64

# с переключением шлейфа 1: «снять/взять → 10 с таймлайн → обратно → 10 с», 2 цикла
python bench_c2000pp.py 192.168.1.10 --zones 1-64 --phases switch --allow-write --test-zone 1 --cycles 2 --hold 10

# всё вместе
python bench_c2000pp.py 192.168.1.10 --zones 1-64 --phases listen,info,single,groups,stress,events,switch --allow-write

# самопроверка утилиты на эмуляторе (без железа)
python bench_c2000pp.py --sim
```

| Фаза | Что делает | Что получите |
|---|---|---|
| `listen` | N с (`--listen`) ничего не шлёт | кто ещё опрашивает, период heartbeat, интервалы чужих ответов |
| `info` | тип/версия/режим/лимиты | |
| `single` | M чтений одной зоны | задержка min/avg/p50/p95/max |
| `groups` | группы 1,2,4,…,64 зон | задержка по размеру; **оценка цикла для 16…512 зон**; рекомендация периода |
| `stress` | запросы подряд при паузе 0/5/10/20/50 мс | потери и запросов/с → какую `gap` можно ставить |
| `events` | чтение 46162 | задержка (не разрушает журнал) |
| `watch` | **ждёт события** `--watch` с, проверяя журнал каждые `--watch-interval` с; каждое событие читает, помечает прочитанным и логирует вместе с текущим состоянием зоны | **разрушающая**, нужен `--allow-write`; в профиль по умолчанию не входит |
| `switch` | команда → таймлайн состояния каждые 0.25 с → обратная команда | время эха, время **первого изменения**, время **подтверждения**, число «морганий»; рекомендация `pending_timeout` |

Задержки считаются «чистыми» — от `sendto` до валидного ответа, без очереди и паузы.
`switch` в конце возвращает шлейф в исходное состояние. Присылайте `bench_*.log`/`.json` — по ним
подбираем `poll_interval`, `group_size`, `gap`, `pending_timeout`.

### Проверка событий (обрыв / пожар / восстановление)

ПП **сам события не присылает**: они появляются в журнале, и их нужно *читать* запросами
(46162 → 46264 → 46163). Поэтому захват «без опроса» содержит только heartbeat конвертера.
Чтобы увидеть события на проводе, запустите опрос журнала и снимайте захват **на машине, которая
опрашивает** (тогда видны и запросы, и ответы):

```bash
# терминал 1 (на машине с интеграцией выключенной!)
sudo tcpdump -i any host 192.168.1.10 -s 0 -w /tmp/events.pcap
# терминал 2: ждём события 3 минуты, чтение каждые 0.5 с
python bench_c2000pp.py 192.168.1.10 --zones 1-16 --phases watch --allow-write --watch 180
# дальше вызываете: обрыв зоны 1 → восстановление, пожар зоны 5 → восстановление, обрыв зоны 1 → восстановление
```

В `bench_*.log` каждое событие будет с кодом, названием, зоной, временем ПП и состоянием зоны на момент
чтения; `pcap_decode.py /tmp/events.pcap` покажет те же кадры на проводе.

### Расшифровка захвата

```bash
tcpdump -i any host 192.168.1.10 -s 0 -w /tmp/capture.pcap
python pcap_decode.py /tmp/capture.pcap --from 192.168.1.10 --to 192.168.1.2
```

## 3. Интеграция Home Assistant

Скопируйте `custom_components/bolid` в `config/custom_components/`, перезапустите HA,
«Настройки → Устройства и службы → Добавить интеграцию → Bolid S2000PP».

### 3.1 Сущности

| Сущность | Что | Примечание |
|---|---|---|
| `sensor` «Шлейф N (IP)» | реальное состояние зоны (текст) + атрибуты `code`, `status`, `armed`, `error` | `unique_id` как в старой версии. При `timeout` — *недоступен* |
| `switch` «Охрана шлейфа N (IP)» | взять/снять | **по умолчанию отключены** — включите нужные. Без «моргания» (pending) |
| `binary_sensor` «С2000-ПП связь» | есть ли валидные ответы; в атрибутах счётчики, RTT, длительность цикла | диагностическая; атрибуты не пишутся в recorder |

### 3.2 Настройки (при добавлении и в «Настроить»)

| Параметр | Ограничения | Описание |
|---|---|---|
| Зоны | `1-20, 25` | какие зоны создавать/опрашивать |
| Период полного опроса, с | **1…3600** | период опроса всех зон |
| Таймаут устаревания, с | 2…7200, **строго больше периода** | иначе форма вернёт ошибку. Рекомендуется ≥ 3× периода |
| Зон в одном запросе | 1…100 (8) | больше — быстрее при сотнях зон; проверять `bench` |
| Читать журнал событий | выкл. | см. §3.3 |
| Создать переключатели | вкл. | |

Смена настроек перезагружает интеграцию; порт 40002 освобождается корректно (ранее на это
время интеграция «уходила в ошибку» с `Address in use`).

### 3.3 «Читать журнал событий» — подробно

С2000-ПП хранит **журнал событий** (256 записей, кольцо): «Пожар», «Тревога», «Взятие/снятие»
(с номером пользователя), «Авария сети 220 В», «Потеря связи с прибором», изменение реле и т.д.
Опрос состояний зон сообщает лишь **текущее** состояние; журнал сообщает, **что происходило**.

Включение даёт:

1. **События в шине HA** `bolid_event` с полями `host, number, code, name, zone, section, user,
   time` — на них удобно строить автоматизации (уведомление «Пожар в шлейфе 3», «шлейф 5 снял
   пользователь 2»).
2. **Быстрое обновление**: при событии по зоне она перечитывается сразу, а не ждёт 10-секундного опроса.
3. **Не теряются короткие срабатывания** между двумя опросами (тревога, которая сбросилась за 3 с,
   опросом по состоянию не видна).

Цена и риски:

* Чтение **разрушающее**: событие, прочитанное одним клиентом, **пропадает** для остальных.
  Если журналом пользуется ещё HUB-C2000PP, SCADA или другой HA — события «разбегутся». Включайте
  только в **одном** месте. Состояния зон от этого не страдают.
* Лишняя нагрузка: один запрос 46162 каждые 2 с (≈ 0.5 запр/с) плюс по 2 запроса на каждое событие.
* Не включайте в конфигурации ПП «Прямую трансляцию событий» — это ломает чтение состояний зон.
* Пример автоматизации:

```yaml
trigger:
  - platform: event
    event_type: bolid_event
    event_data: { code: 37 }          # 37 = «Пожар»
action:
  - service: notify.mobile_app_phone
    data: { message: "Пожар, шлейф {{ trigger.event.data.zone }} ({{ trigger.event.data.time }})" }
```

### 3.4 Несколько клиентов одновременно (HA + ПК)

Конвертер присылает ответы **на все** прописанные IP, поэтому HA видит и то, что запросил ПК:

* чужая **команда** взять/снять зону распознаётся по эху записи → переключатель этой зоны
  сразу показывает целевое состояние, зона перечитывается быстрыми шагами;
* чужой **запрос чтения** (адрес регистра в ответе не передаётся) → HA делает внеплановый опрос
  всех зон, не чаще раза в 3 с.

Ограничение: пока HA ждёт свой ответ, чужой ответ **той же формы** может быть принят за свой; через
секунды данные исправит внеплановый опрос. Для строгости опрашивать должен один клиент.

### 3.5 Подбор периода (оценка, уточняется `bench`)

| Зон | Цикл, группа 8 | Цикл, группа 32 | Разумный период |
|---|---|---|---|
| 16 | ~0.2 с | ~0.1 с | 1–2 с |
| 64 | ~0.6 с | ~0.2 с | 2 с / 1 с |
| 128 | ~1.3 с | ~0.4 с | 3–5 с / 1–2 с |
| 256 | ~2.6 с | ~0.7 с | 6–10 с / 2 с |
| 512 | ~5 с | ~1.4 с | 10 с / 3–4 с |

Исходные данные: одиночное чтение ≈ 40–70 мс (оценка по `pcap`), пауза между запросами 20 мс.
Если цикл дольше периода, в лог HA пишется предупреждение, а `last_poll_duration_s` виден в
атрибутах «связи».

## 4. Диагностика

| Симптом | Причина / действие |
|---|---|
| `Address in use`, интеграция «не готова» | порт 40002 занят: второй процесс (HUB, `bench`, скрипт, дубль интеграции). Закройте его; при смене настроек интеграции порт теперь освобождается сам |
| все зоны `timeout`, «связь» выкл. | нет ответов: проверьте IP конвертера, что IP HA прописан в С2000-Ethernet, порт, адрес `slave_id` |
| `bad_frames` растёт | битые кадры (CRC/длина); смотрите лог `-v` |
| `unmatched` растёт | приходят ответы на чужие запросы или запоздавшие — при двух IP в конвертере это норма |
| `lost_by_counter` растёт | реально теряются UDP-ответы конвертера (heartbeat уже учтён) |
| зона `no_data` | ПП отвечает exception 3: зоны нет в БД ПП или нет данных |
| состояние всё время «Восстановлена связь с прибором» (251) | ПП не знает реального состояния (режим Slave, мастер ещё не передал) |
| команда → `exception 4` | нет связи с прибором или управление зонами запрещено в конфигурации ПП |
| шлейф взят, но вернулся | `Неудачное взятие` (17): шлейф нарушен в момент взятия |

## 6. Что изменилось в 2.1.0 (относительно 2.0.0)

* HA: смена настроек больше не даёт `Address in use` (ожидание закрытия сокета + повтор bind).
* HA: ограничения настроек — `stale_timeout` > `poll_interval`; период опроса от 1 с; параметр
  «зон в одном запросе»; подсказки к полям; английский и русский переводы.
* Переключатель шлейфа не «моргает»: ожидаемое состояние (pending) до подтверждения ПП,
  быстрые перечитывания зоны после команды.
* Чужие команды (эхо записи) распознаются точно и обновляют именно свою зону.
* Исправлено: в «взята» входил код `174` (это приоритет, а не код состояния).
